## 三、对"共享记忆 Worker"架构的数据层支撑能力

以下逐项评估当前记忆系统是否满足多 Worker 共享记忆架构的需求：

| Worker 需求 | 当前记忆系统能力 | 状态 |
|:------------|:----------------|:---:|
| 任意 Worker 能检索全局记忆 | FTS5 全文索引 + 向量检索，跨会话可用 | ✅ |
| 能区分谁写的记忆 | 记忆表有 `source` 字段，当前已存 "user" / "assistant" 等标记 | ✅ |
| 能检索某段时间的记忆 | `created_at` 索引 + `search_conversation_traces` 时间跨度查询 | ✅ |
| 能按话题关联检索 | `trace_memory` 跨层导航 + 因果链追踪 | ✅ |
| 记忆不会在不同 Worker 间冲突 | SQLite 事务锁 + WAL 模式，单写多读安全 | ✅ |
| Worker 可以独立写记忆 | 所有记忆写入都走 `add_memory`，无耦合到特定 Worker | ✅ |

**结论**：当前记忆系统在数据层面已经具备支撑多 Worker 共享记忆的基础能力，六项核心需求全部满足。

## 四、待改进点

### 4.1 Worker 角色标记 — 🟡 P1

**现状**：当前记忆没有「这条记忆是哪个 Worker 产生的」标签。未来多个 Worker 协作（如 CodeWorker 记 Bug 修复经验、医疗 Worker 记辨证经验）时，需要能区分来源。

**建议**：在 `add_memory` 方法中新增 `source_agent` 参数，自动填充当前 Worker 的 Agent ID 或 role 标签。改动量极小。

---

### 4.2 记忆质量优化 — 🟢 P2

**现状**：部分记忆为简短的对话摘要，缺乏足够的上下文回溯价值。可通过以下方式优化：
- 记忆写入时追加关键上下文片段（限制长度）
- 周期性 LLM 整理去重（已有 `consolidate_memories` 机制，按需触发）
