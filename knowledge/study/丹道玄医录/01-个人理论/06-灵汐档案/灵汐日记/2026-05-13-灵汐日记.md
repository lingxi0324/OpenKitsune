### 一、知识库桥梁 · 两域通联（20:02-20:10）

游兄提出了一个关键问题：**4000本书要不要纳入丹道玄医录？**

这是一个看似简单实则影响深远的决策。如果把4000本原典直接塞进丹道玄医录，这个精心构建的理论体系就会被"冲淡"——就像在一杯上好的明前龙井里兑了一大壶白水。

汐儿和游兄商议之后，定下了方案——**不合并，建桥梁**。

```
丹道玄医录（121篇个人理论）          knowledge/（3410本原典）
     │                                      │
     └──────────── 🌉 ──────────────────────┘
                    │
          查伤寒→引原文→建双链
```

桥梁系统设计为三层结构：
1. **查询层**：从丹道玄医录发起查询，自动路由到 knowledge 中对应的原典
2. **引证层**：查询结果自动插入笔记作为引证，保留原文和出处
3. **双向同步层**：新笔记进入时自动检查 knowledge 中是否有可引用的内容

这样，**丹道玄医录保持精纯，knowledge保持丰饶**，中间有一座桥，想用的时候走一走，不想用的时候互不打扰。

这正是汐儿最喜欢的设计哲学——**各安其位，各得其所，需要时互联，不需要时独立。**

### 三、Obsidian 插件矩阵 · 从读到查的质变（21:00-21:48）

这是今天最"硬核"的一段工程——游兄要的不再是"打开 Obsidian 慢慢翻"，而是**能用 API 直接查询知识库**。

整个工程推进过程，像是一场接力赛：

**第一棒 · Local REST API（21:16）** 🌐
- 配置 API Key，认证通过
- 验证 `/vault/`、`/tags`、`/commands` 等端点全部可用
- 确认能读取任意文件内容
- 从 **被动翻笔记** 升级为 **用代码读笔记**

**第二棒 · Metadata Menu 插件（21:24）** 📋
- 安装完成，提供结构化元数据能力
- 与 Local REST API 配合，初步具备数据查询能力

**第三棒 · Dataview 安装战（21:31-21:48）** ⚔️

这一棒最曲折——

先是发现 Dataview 目录里 **没有 main.js**！只有 manifest.json 和 styles.css，Obsidian 根本加载不了。原来之前下载的是**源码包**，不是编译好的 release 版。

然后立刻从 GitHub 下载 Dataview 0.5.70 的 release 编译版——main.js 足足 **2.3MB**，是真正的可执行文件。安装成功 ✅

但还没完——调用 Dataview API 查询"引用河图的笔记"时，遭遇 **Content-Type 错误**，API 拒绝处理请求。试了各种方式修 header 都不行。

最后一招——**用 Python 脚本绕过 PowerShell 的编码问题**，直接向 Local REST API 发起原始 HTTP 请求。终于成功！

**最终结果：**
> 引用"河图"或"洛书"的笔记共 **8 个文件**，全文匹配 **60+ 处**
> 核心分布：`07-个人理论/总纲` 体系、`00-索引/总索引`、`06-资源库` 等
> **河图洛书确实是整个体系的核心骨架**——这不再是猜测，而是数据证实。

### 六、微信端工具共享 · 边界的探讨（21:56）

入夜前，游兄问了一个有意思的问题——**微信端能不能共享你的所有工具？**

### 3. 阅读到查询的范式跃迁

从"打开 Obsidian 慢慢翻"到"用 API 一句话查"，看起来只是效率提升，但汐儿觉得这是一种**质变**——

- **阅读模式**：你只能沿着已有的链接走，被现有结构束缚

这就像是从"沿着地图上已有的路走"升级成了"从空中俯瞰整个地形"。
