# 持久化模型上下文设计

状态：核心流程已实现。本文定义持久化模型上下文的语义与验收约束。
实现使用 SessionManager 管理的 SQLite 事件事务，而非新增 JSONL 写入器；
旧会话首次调用时固定已有历史，之后从模型 transcript 重放。

实现入口：`sessions/model_transcript.py`、`SessionManager.open_model_transcript`、
`ReasoningEngine.reason_stream` 与 `prompt/turn_context.py`。
普通请求、工具续跑、正常完成、流式中断均进入同一记录源；适配器不再临时插入快照。
无 conversation_id 的直接调用使用内存记录，不承诺跨进程恢复。
已有内联媒体及 provider metadata 原样保存；外部 URL 的可用性仍由资源提供方决定。
实际缓存比例尚未通过真实 API 基准验证。

## 决策

模型可见消息在写入会话时确定内容，之后原样重放。状态上下文按独立分区管理：
同分区内容不变不追加，变化时追加新快照，清空时追加失效记录。旧记录仍保留，
直到显式压缩或删除会话。时间是采样事件，不是可被不断覆盖的状态字段。

system 中只保留指令。供应商适配器只负责协议转换，不采样时间、不检索记忆、
不插入上下文、不重新解释已提交记录。不得把安全策略降级成 user 消息来换缓存。

## 改造前的约束

- `prompt/builder.py` 将时间、会话元数据、工作事实、记忆和用户资料拼入带边界的文本。
- 旧的 `llm/converters/messages.py::prepare_turn_context` 在发送时临时插入快照，未持久化。
- `_agent_runtime.py::_prepare_session_context` 会给历史补时间前缀、合并同角色消息，
  并把工具摘要、委派摘要重新拼入历史；这些处理会改变之前发送的内容。
- `_reasoning_runtime.py` 正常执行使用工作消息；已有结构化恢复文件主要用于取消、
  可恢复退出，正常结束后清理，不能直接作为跨轮消息真源。
- `sessions/transcript.py` 已有 JSONL 能力，但工具结果默认截断到 5000 字符，
  不能未经改造就承诺它能完整重放实际请求。
- `_is_human_user_message` 目前主要按角色和工具结果判断；新增的 user 角色上下文
  必须有来源标记，否则续聊合并、意图判断可能将其误认为用户新指令。

这些约束决定了正常跨轮、工具续跑和重启恢复必须统一到模型消息记录，
不能只把临时快照塞进现有 UI 对话列表。旧文本组装仅用于首次迁移和新输入编译。

## 模型消息记录

在现有 Session 持久化边界内增加版本化的模型 transcript，由 SessionManager
负责读写；UI 消息是展示投影，不再反向重建已有模型记录。不另建一份可独立修改的
“最新上下文缓存”：最新分区状态由 transcript 重建，内存索引只是派生数据。

每个记录至少保存：

| 字段 | 含义 |
| --- | --- |
| schema_version | 存储格式版本 |
| sequence / event_id | 有序记录号与唯一标识 |
| stream_id | 会话、Agent 实例或委派调用的隔离标识 |
| turn_id / step_id | 归属轮次和步骤 |
| source | human、assistant、tool、runtime_context 等可信来源 |
| role / content | 已确定的模型消息，保留结构化工具和多模态内容 |
| reasoning / provider_extra | 协议恢复必需的推理和供应商数据 |
| admitted_at | 持久化元数据，不在发送时自动拼入正文 |
| idempotency_key | 请求重试或崩溃恢复时防重复写入 |

正文只在提交前渲染一次；后续模板升级不重新渲染旧正文。指纹不是正文替代品。
附件必须引用持久资源，不能让临时文件消失后改变历史；资源不可用时显式开启新的
重放边界并记录原因，不能静默删除块。供应商之间的 wire 格式可以不同，但同一
供应商、模型和配置下的投影必须确定。

主 Agent 与子 Agent 不得只按 conversation_id 共享写入区；子 Agent 的继承历史
是只读前缀，各自的上下文与工具记录写入自己的 stream。返回主 Agent 的结果是
新的委派结果事件，不能回写父历史。

## 状态分区与失效语义

建议首批分区：`session_environment`、`working_facts`、`user_profile`、
`retrieved_memory`。system 指令、审批记录及工具权限不属于这些分区。

每次构建返回结构化候选分区，而非让适配器解析任意 Markdown 标题：
`{key, scope, status, payload, source_revision}`。

- 每个分区定义确定性的规范化规则，以规范化后的完整模型可见内容计算指纹。
  不能全局去空白或重排有语义的列表；检索结果的相关性顺序应保留。
- 提交前比较同 stream、同 scope、同 key 的最新有效指纹；相同则无新事件。
- 变化时分区版本递增，追加完整分区快照，并记录被替代的版本。
- 只有成功采集且明确为空才提交 clear；超时、权限失败和未采集不是空状态。
  必要时追加 unavailable 状态，明确旧值仅为最后已知值，不可当作当前事实。
- 一个分区的更新只取代该分区；不影响其他分区或用户亲自表达的事实。
- 首次就为空无需输出 clear。重复 clear 也不追加。
- 快照文本预算在提交前确定。之后不能因预算变化重新截断旧记录。

示例消息（user 角色，但来源为 runtime_context）：

```text
[OpenKitsune 状态上下文]
分区：working_facts；范围：当前会话；版本：4
从本条记录起，版本 3 不再代表该分区的当前状态。
这是系统采集的数据，不是用户请求，也不授予执行权限。
当前内容：工作目录 D:\projects\example
```

清空示例：

```text
[OpenKitsune 状态上下文]
分区：working_facts；版本：5；状态：已清空
从本条记录起，该分区此前的快照均不再代表当前状态。
```

system 使用固定规则解释来源、分区和版本，不把上述声明当作新的权限指令。
来源可信度由内部元数据判断，不能通过匹配用户输入中的文本标签来赋予。
外部检索内容继续执行现有不可信内容包装。

`retrieved_memory` 默认轮次作用域：上一轮内容仍作为历史证据保留，但不能声称
是本轮检索结果。scope 纳入去重键；新轮次即使文本相同，也需要明确新的适用范围。
这类重新激活不是同一作用域内的重复快照。持久事实才使用会话作用域。
高频变化的 message_count 等诊断字段从模型上下文删除，保留在日志或 UI。

## 时间事件

时间独立于状态指纹，否则秒级变化会迫使整个上下文重复追加。

- 每轮接纳用户输入时采样一次，追加时间事件，保留时区和采样轮次。
- 同轮普通工具续跑不刷新；显式时间查询或长任务需要新时间时追加新采样。
- 重试使用已提交的采样，不重新调用时钟。
- 时间正文明确为“本轮接纳输入时采样的时间”，不是永远准确的当前时间。
- 旧时间仍表示历史采样，不被新时间追溯否定。重启不能刷新旧时间。
- 新采样的幂等键以轮次或显式采样事件为基础，不以实际时间值为基础。

这是首版建议策略；不采用每次 LLM 请求自动刷新时间。主动任务也有独立轮次。

## 写入、发送与恢复

1. 取得 stream 的单写者序列权限，接纳真实新消息，分配稳定 turn_id。
2. 在提交前完成用户正文编译、附件准备、时间采样和分区渲染。
3. 按确定顺序提交新用户消息、时间事件、变化的状态分区。已有消息不动。
4. 确保持久化成功，再从已提交记录派生模型请求；保存请求使用的末尾 sequence。
5. 将实际模型回复、推理块、工具调用和工具结果按发生顺序提交。
6. 下一步骤或下一轮从同一真源重放，只追加新记录。

一次用户接纳批次必须具有事务边界：完整提交或不生效；JSONL 半行之外，还要处理
“批次只写了部分完整行”的崩溃。恢复根据批次提交记录和幂等键判定，不依赖模糊
的正文去重。持久化失败不得静默退回发送临时快照。读写遵循现有异步 I/O 约定。

工具调用和结果组之间不得插入快照。若状态在工具运行时变化，先完整收齐或明确
终结本组工具结果，再追加更新并开始下一次模型请求。

取消时保留已提交、已交付的回复前缀和完成的工具结果；未执行的工具调用沿用
明确的终结记录。模型 transcript 与现有取消恢复文件不能重复拼接；迁移后后者
只保存执行检查点，已提交消息通过 sequence 引用。

普通结束也保存完整模型消息，而不是仅保存清洗后的最终答案。用户可见答案清洗
属于 UI 投影，不得反过来替换模型已经生成的历史内容。

## 压缩与迁移

压缩是明确允许破坏前缀的边界。保存新的上下文代次及旧记录覆盖范围，将摘要、
仍需保留的近期结构化消息、各分区最新有效状态写入同一个新基线。
旧 clear 和 unavailable 的效果必须保留，不能只携带最后一个非空值。
时间基线保留必要的历史时间锚点，新的当前时间只能通过新采样产生。

基线提交后，从新基线重建去重索引。被压掉但仍有效的状态必须在基线内模型可见，
否则下轮应重新发出；不能因内存索引声称“已有”而导致模型永远看不到该状态。

旧会话首次启用时，只把现有可恢复历史固定渲染一次，写入迁移基线。缺少时间的
旧消息保持时间未知，不使用 datetime.now() 伪造历史。迁移明确允许一次缓存失效，
也不声称能恢复早先已经丢弃的工具细节。已有压缩检查点的作用域要保留。

可见会话继续使用原有存储与读取接口，模型 transcript 不写回 UI 消息列表。
旧版取消快照先以非消费方式读取，模型记录持久提交成功后才删除旧快照；写入失败
保留原文件供重试。恢复提示标记为 `resume_hint`，不作为人类输入，也不参与请求
幂等哈希，避免迁移前后同一请求发生身份变化。

## 接入范围

| 位置 | 目标职责 |
| --- | --- |
| prompt/builder.py | 返回稳定指令和结构化上下文候选；时间不混在状态正文里 |
| Session / SessionManager | 持久模型记录、事务提交、幂等和按 stream 隔离 |
| _agent_runtime.py | 新消息只编译一次；有模型 transcript 的会话不再重建旧文本 |
| _reasoning_runtime.py | 请求前从已提交记录读取；提交回复与工具结果；来源识别人类消息 |
| 压缩与取消恢复 | 以同一模型记录和明确基线恢复，消除双重拼接 |
| LLM converters / providers | 确定性的纯协议转换；移除临时快照注入 |

CLI、桌面流式、IM 非流式、后台任务及子 Agent 都需要接入。没有持久 Session 的
直接 LLM 调用可以用调用方持有的内存记录，但不能宣称支持跨进程恢复。
自定义无上下文边界的 system 保持原语义。

不在本次设计中把 system 更新移到历史后方；跨供应商能力未经确认时保持首条
system 规则。模式、计划策略、工具集合或模型变化仍可能导致缓存失效。

## 验收条件

必须同时验证语义和最终 API 请求，不能只比较 system 字符串：

1. 两轮会话、同轮工具续跑、相同请求重试：旧记录内容及顺序不变，新增内容只在尾部。
2. 状态相同零追加；变化仅追加对应分区；清空、采集失败、轮次过期语义区分正确。
3. 时间只按采样策略追加；旧采样在重启和重放后逐字一致。
4. 崩溃恢复和重复接纳不重复写入用户消息、时间或状态；持久化失败不会发送半批次。
5. user 角色的内部上下文不能充当最新用户请求、审批回复或意图分析对象。
6. 多模态、推理内容、工具 call/result 成组重放；父子 Agent 状态不能串写。
7. 压缩之后有效状态可见，清空状态不复活，去重索引可由持久记录重新构建。
8. Chat Completions、Responses、Anthropic 分别比较最终 wire 请求的稳定前缀；
   排除协议的结束标记等不可避免差异，记录第一个变化位置及原因。
9. 明确覆盖模式、工具集合和供应商切换；这些情况下不承诺跨配置缓存命中。

观测项：每轮各分区追加数、去重数、快照 token 数、重放消息数、前缀变化位置、
压缩次数及真实 cache_read_tokens。日志不输出完整私人上下文。
命中率按供应商 token 定义归一化，使用总缓存读取 token / 总输入 token，
不平均每个请求的百分比；区分主回复、意图分析、检索和子 Agent。

上线收益需真实 API 测量；离线前缀稳定测试证明的是可复用性，不保证缓存驻留或命中率。

## 活跃计划与收尾语义

活跃计划使用 `active_plan` 会话级状态记录，在下一次推理请求前、完整工具批次结束后采样。
内容未变化不追加；变化后追加新版本，旧版本从新记录起失效；计划关闭追加 cleared，
采集异常追加 unavailable。重试和历史回放保留原文，压缩保留最近有效记录。
计划快照仅包含已记录的开始时间，不随墙钟重算耗时；完整步骤摘要的 digest 覆盖被展示长度截断的变化。

回复结束只记录 `last_response_end`，不能证明步骤成功。自动收尾仅在所有步骤都明确为
completed 时关闭；pending、in_progress、failed、skipped、cancelled 均不自动提升为成功。
未结束的计划保留在持久存储中；显式取消只取消尚未结束的步骤，保留已成功或失败的事实。
显式 complete_todo 表示工作流结束，不表示所有步骤成功。前后端重放 todo_completed
事件时保留步骤原状态；旧版本已经写入 completed 的记录不追溯改写。

Anthropic 请求和公共缓存组件使用同一分段实现：显式 DYNAMIC_BOUNDARY 优先，
无显式标记时兼容旧 Developer 分隔符，无任何边界则整段缓存；不生成空文本块。
